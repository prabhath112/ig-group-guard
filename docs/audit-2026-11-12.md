## 2. Prioritized, minimal fixes

### P0 — close the "button becomes tappable" holes (#1, #3)

**#1 Transient-null tear-down + consent/confirm reset.** Root cause: the `button==null` branch calls `hide()` **unconditionally** (l.157) *before* the grace re-poll, so a single null frame removes the overlay, flips `allowedThisSheet=false` (l.426-428) and `dismissConfirm()` (l.425). The grace mechanism exists to tolerate exactly this but `hide()` defeats it.

Minimal fix — in `refresh()` (`GroupGuardService.java:151-171`), keep the existing overlay in place while grace is live instead of tearing it down; arm grace **edge-triggered** so a genuinely-closed sheet still expires:

```java
if (button == null) {
    long nowMs = SystemClock.uptimeMillis();
    boolean wasTracking = window != null || !lastButton.isEmpty();
    if (wasTracking && graceUntil <= nowMs) {           // edge-trigger: arm once per vanish
        graceUntil = nowMs + GRACE_MS;
    }
    if (nowMs < graceUntil) {
        // ponytail: transient loss (null root / isVisibleToUser flicker) must NOT uncover an
        // already-covered or user-approved button. Leave the overlay, confirm popup and
        // allowedThisSheet exactly as they are; just keep looking.
        handler.postDelayed(recheck, GRACE_STEP_MS);
        return;
    }
    hide();                                             // grace expired: sheet really gone
    handler.postDelayed(recheck, WATCH_STEP_MS);
    return;
}
```

This single change resolves raw findings **309(overlay), 427, 426, 157, 425** — the overlay, the per-sheet consent, and the open confirm dialog all survive a transient null. `hide()` keeps resetting `allowedThisSheet`/`dismissConfirm` only on the genuine paths (grace-expiry above, `fg==0` hibernate at l.146, `onInterrupt`/`onDestroy`).

> Note: leaving a *stale* overlay in place for up to `GRACE_MS` means the grey bar covers the button's last-known rect. That is correct — the button has not moved; the null is a render frame, not a layout change. When it reappears at the same spot the `place()` no-op guard (l.355) keeps it pinned.

**#3 `place()` failure kills the poll.** In `refresh()` at `GroupGuardService.java:237`, reschedule before bailing:

```java
if (banner == null) {                  // window could not be (re)added
    handler.postDelayed(recheck, WATCH_STEP_MS);   // honour the catch's "re-add next time"
    return;
}
```

That is the whole fix — the `updateViewLayout` catch at l.411 already says "re-add next time"; this gives it a next time.

### P1 — the deep-fallback decision (#2)

Finding #2 is real **in the code** but its trigger (group button in a **non-active** window) is **unverified** — the only ground truth (uiautomator on IG 455, l.48/304-307) shows it in the active window. The `getWindows()` fallback (l.310-315) is therefore currently **either load-bearing-but-broken or dead code**: every sustaining poll is `deep=false`, so whatever the deep scan finds is dropped 300 ms later.

Lazy, decisive path — **don't build deep-recheck machinery for an unproven case.** Instead:

1. Run one real `uiautomator dump` on the current IG while the share sheet is open (RT01 already needs a human; add this capture).
2. **If** the button is ever in a non-active window → make the sustaining recheck deep *only while an overlay is shown* (follow stays shallow — it only runs mid-slide when the button is present): change the `recheck` Runnable (l.64-66) to `refresh(window != null)`.
3. **If** it is always in the active window (expected) → **delete the `getWindows()` fallback** (l.310-316) and the `deep` parameter entirely. That removes the whole #2 cluster, the main-thread cost of `getWindows()` on every event, and simplifies `findGroupNode`/`selectedCount`/`refreshNow`.

Either outcome is a smaller, more honest codebase than shipping a fallback no poll can sustain.

### P1 — crash guard (#4)

CharSequence pkg = root.getPackageName();

### Perf / latency tuning (the "fastest banner" tradeoff) — #9 + #11

The user chose fastest banner, so **do not raise `WATCH_STEP_MS` (120 ms), `RECHECK_MS` (300 ms) or the 16 ms follow** — those cadences are what make the banner appear instantly, and each shallow scan is genuinely cheap (one active-window tree walk). The real waste is the **unbounded `fg==null` poll (#9)**: bound *that case only*, leaving the in-Instagram cadence untouched.

In `refresh()`, add a null-foreground counter and back off after a short deadline (keep it tiny — one int field):

```java
// field: private int nullStreak;
Integer fg = foregroundIsInstagram();
if (fg != null && fg == 0) { nullStreak = 0; /* hibernate as now */ ... }
if (fg == null && window == null && lastButton.isEmpty()) {
    // not in a sheet, root persistently null (keyguard / secure app): stop fast-polling
    if (++nullStreak > NULL_BACKOFF_POLLS /* e.g. 16 ≈ ~2 s */) return; // event-only until IG returns
} else {
    nullStreak = 0;
}
```

This keeps the correctness win the comment at l.161-167 was defending (a transient null during an open sheet still polls, because there `window!=null`/`lastButton` is non-empty so the back-off is skipped) while killing the forever-8 Hz drain behind a secure app. Collapses all six raw `fg==null` findings.

**Node recycling (#11)** also *reduces scan cost* on the Android 8.x hot loop, so it belongs in this bucket. Guard with SDK (recycle is a no-op/deprecated on API 33+):

- In `findIn` (l.319-327): after extracting the target, `recycle()` the `root` arg's query results you don't return and the intermediate `getParent()` chain.
- In `findGroupNode` (l.308-316): recycle the active-window root when falling back, and each `w.getRoot()` that didn't match.
- In `collectText` (l.339-343): recycle each `getChild(i)` after the recursive call.
- Wrap every `recycle()` in `if (Build.VERSION.SDK_INT < 33)`.

Keep only the single returned target node alive up the chain. This is the one item the user explicitly called out and it is a genuine pre-API-33 pool leak.

## 3. Completeness critic — what the audit did NOT cover (and should have)

1. **Orientation / display-configuration invalidation of `home` (likely Medium, uncovered).** `home` is an absolute-screen `Rect`, persisted to disk and reloaded on connect, but nothing invalidates it on rotation, split-screen, font-scale, fold/unfold, or a different device after a backup-restore. After a rotation the remembered rest position is wrong, so `towardsHome`/`backDownHome` place the banner (and its tap-swallowing window bounds) at the old coordinates — the grey bar lands off the button and, worse, the window may not cover the real button → **tappable**. There is no `onConfigurationChanged`/display listener anywhere. This is a plausible real-world "button exposed" path the audit missed entirely.

2. **No unit/integration coverage of the `refresh()` state machine.** All testing is `e2e.py` against a fixture; the branch-heavy `refresh()` (grace, opening, towardsHome/backDownHome, allowedThisSheet) has zero JVM-level tests. Every bug above lives in that method. A small Robolectric/plain-JUnit harness around `refresh()` transitions (feed a sequence of button rects incl. nulls) would have caught #1, #3, #12 directly and is the highest-leverage missing guard.

3. **Behavior when consent is false but the service is running.** `findGroupButton` returns null every poll (l.150), which enters the same unbounded-poll path as #9 — a consented-off but enabled service can fast-poll indefinitely. Not called out.

4. **Android 14/15 accessibility-overlay and foreground-service constraints.** `TYPE_ACCESSIBILITY_OVERLAY` behavior, `FLAG_LAYOUT_NO_LIMITS`, and cutout handling on API 34/35 are unverified; the audit stopped at the Android 8.x floor and never checked the ceiling.

5. **Post-settle button movement on Android 8 with no event.** The code relies on `RECHECK_MS=300` to catch GONE on A8, but if IG *moves* (not removes) the button after it settled and sends no event, the overlay stays at the stale spot for up to 300 ms with the real button beside it exposed. Partially implied by #1 but never analyzed as its own case.

6. **Battery claims are reasoned, not measured.** Every "8×/sec drain / blocks doze" statement is static reasoning. `Handler.postDelayed` holds no wakelock (one verify note correctly flags the "blocks doze" wording as wrong), so the real cost needs a Batterystats/`dumpsys` measurement that was never taken. Tune #9 off a measurement, not the estimate.

7. **RTL / non-English locales.** `sameColumn` uses `left/right` equality (fine), but the text fallback is English-only (`GROUP_BUTTON_TEXT`, acknowledged in-code) and column logic under RTL layouts was not examined.

8. **Confirm popup has no back-button / dismiss affordance** (`FLAG_NOT_FOCUSABLE`) and no timeout — only tap-outside or a null-poll (the very bug in #1) dismisses it. Minor UX gap, uncovered.

9. **Thread-model statement is missing.** Everything runs on the main looper (so the plain `refreshScheduled`/`home`/`allowedThisSheet` fields are safe), but `running` is `static volatile` and read/written across the tile, activity, and service — the audit never stated or checked the concurrency model, which is the kind of thing that bites on service restart.

Of these, **#1 (orientation invalidation of `home`)** and **#2 (no `refresh()` unit tests)** are the two gaps worth acting on now; the rest are lower-probability or measurement/documentation items.
